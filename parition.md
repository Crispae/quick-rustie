# Content-Based Partitioning and Centroid Pruning for Search over Object Storage: A Literature and Systems Review for Adding Vector Search to Quickwit

The evidence strongly favors a centroid/cluster-based (IVF/SPANN-family) vector index over graph indexes for an object-storage engine like Quickwit, because bounded round-trips and contiguous range-GETs matter more on S3 than graph-hop efficiency. The biggest open design problem is not query-time routing but keeping clusters good across splits and merges. The strongest pattern in production systems is two-level: IVF inside each immutable segment, with centroids reused and refined at merge time, and optionally a global coarse codebook that lets the metastore prune whole splits.

## TL;DR

- **Use a centroid-based index, not HNSW/DiskANN, for S3-resident splits.** turbopuffer (SPFresh-derived hierarchical clusters), Elasticsearch DiskBBQ (hierarchical k-means IVF), LanceDB (IVF-PQ/IVF-RQ on Lance), Pinecone serverless (geometric partitioning over blob storage) and SPANN all converge on "small centroid index in memory, cluster posting lists on disk/object storage." turbopuffer reports that this caps a cold query at the height of its cluster tree in object-storage round trips.
- **Merges are the crux, and the literature offers incremental answers.** SPFresh/LIRE (split/merge/reassign boundary vectors), DeDrift (lazy centroid recomputation plus splitting), Quake (cost-model-driven split/merge), Ada-IVF (locality-aware maintenance, which its authors report gives an average 2x and up to 5x higher update throughput than prior dynamic IVF maintenance while matching query throughput), and the "seed the merged segment's k-means with the input segments' centroids" technique (reported for Elasticsearch's IVF code) all avoid full re-clustering. For Quickwit, merge-time centroid reuse plus local refinement is the natural fit.
- **Text-side content clustering is well established but gives different gains.** Selective search (Kulkarni & Callan, SIGIR 2010 LSDS workshop) found that topic-based shards cut search cost "to less than 1/5th of that of the exhaustive search without reducing search accuracy" across three datasets. Recursive graph bisection (BP), already in Lucene as `BPReorderingMergePolicy`, shrinks postings and speeds queries *within* a segment. For hybrid queries, turbopuffer's "native filtering" (attribute indexes keyed by cluster ID) is the clearest published way to reconcile inverted-index pruning with cluster pruning.

## Key Findings

1. **Object storage changes which ANN family wins.** Graph indexes (HNSW, DiskANN/Vamana) need many *dependent* random reads. turbopuffer states that with a cold SSD cache its clustering index needs "at most 2 round-trips to object storage," versus graph structures that "would easily require a dozen or more roundtrips." In its ANN v3 write-up, the hierarchy "bounds the number of round-trips to object storage to the height of the SPFresh tree." Cluster indexes also give spatial locality: similar vectors are stored contiguously, so fixed-size reads waste little.
2. **Centroids are the "zone map" of vector space.** In IVF/SPANN, a centroid summarizes a posting list the way min/max summarizes a column block. turbopuffer's centroid tree uses a ~100x branching factor so that "if we can fit all data vectors on SSD, we can fit all centroid vectors in DRAM." This maps directly onto Quickwit's hotcache/footer idea.
3. **Cluster quality degrades under updates, so maintenance is mandatory.** Ada-IVF measured rising partition-size imbalance and reconstruction error as an IVF index takes inserts and deletes. DeDrift (Baranchuk, Douze, Upadhyay & Yalniz, ICCV 2023) found on real media workloads that "unless a costly index reconstruction is performed frequently, content drift degrades the search accuracy and efficiency."
4. **Segment-per-index systems are the closest analog to Quickwit.** Lucene/Elasticsearch (DiskBBQ per segment), Milvus (index per sealed segment) and Pinecone (index per slab, with fancier indexes built on compaction) all build a vector index per immutable segment and rebuild or refine it on merge. Only turbopuffer and Milvus's clustering compaction try to align *segments themselves* with content.
5. **Filtered and hybrid search needs the two indexes to cooperate.** Pure pre-filtering is exact but slow; pure post-filtering can reach 0% recall. ACORN (graph) and turbopuffer native filtering (clusters) are the two main published answers.

## 1. Cluster-Based and Partition-Based ANN Algorithms

**IVF / IVF-PQ (Faiss family).** k-means partitions the space into `nlist` Voronoi cells. Each vector goes into the posting list of its nearest centroid, and a query scans the `nprobe` nearest cells. PQ compresses the vectors in each list. LanceDB's docs describe the same mechanism: centroids come from k-means over the stored vectors, and "during a query the centroids are compared with the query vector to find the closest partitions." Milvus's IVF_FLAT and IVF_SQ8 "implement the k-means clustering method," dividing the space into `nlist` clusters. *Updates:* new vectors are just assigned to their nearest existing centroid. Centroids are never retrained unless you rebuild, and that is exactly how drift arises.

**SPANN (Microsoft, NeurIPS 2021).** A memory–disk hybrid that "follows the inverted index methodology," storing "the centroid points of the posting lists in the memory and the large posting lists in the disk." *Clustering:* hierarchical balanced clustering limits and equalizes posting-list lengths, because disk reads scale with list length. Lists are also *augmented* with boundary vectors ("points in the closure of the corresponding clusters"), so a vector near a border sits in several lists. The Vespa team's analysis notes the paper sets the cluster count at 4–20% of the number of vectors, and centroids themselves are indexed with an in-memory ANN (SPTAG). *Routing:* find the nearest centroids, then apply "a query-aware scheme to dynamically prune the access of unnecessary posting lists." *Result:* over 2× faster than DiskANN to reach 90% recall at the same memory cost on three billion-scale datasets. SPANN is essentially the blueprint for turbopuffer's centroids-local/clusters-remote design.

**SPFresh / LIRE (SOSP 2023).** Adds in-place updates to SPANN. Its critique of the status quo: "existing systems maintain a secondary index to accumulate updates, which are merged by the main index by global rebuilding the entire index periodically," causing latency/accuracy swings and heavy rebuild cost. *LIRE* (Lightweight Incremental REbalancing) splits oversized partitions, merges undersized ones, and reassigns vectors only "at the boundary between partitions," on the premise that in a good index such vectors are few. The slides describe split → reassign → possible cascading splits, with a convergence proof. *Result:* 2.41× lower P99.9 latency than baselines under a simulated 1%-daily-update workload, on a single machine at billion scale. *Criticism:* a 2026 paper on graph-based in-place updates (Yi) reports SPFresh starting at 67.8% recall on its benchmark "due to its coarse-grained, cluster-based index design" and says it "cannot deliver high throughput and high recall at the same time." LSM-VEC similarly argues SPFresh "trades accuracy for update speed." These are competitor claims on their own benchmarks, but they fit the general view that cluster indexes buy updateability and I/O locality at some recall cost.

**ScaNN and SOAR (Google).** ScaNN partitions with k-means and quantizes anisotropically for maximum inner product search (MIPS). SOAR (Sun, Simcha, Dopson, Guo & Kumar, NeurIPS 2023) adds controlled redundancy: each vector gets a secondary cluster chosen so its residual is near-orthogonal to the primary one. "When one assignment estimates badly the other is likely to estimate well." A third-party analysis puts SOAR's storage overhead at about 10–20%. SOAR is the principled version of SPANN's boundary duplication, and Elasticsearch has adopted it for DiskBBQ-style spill assignments (see below).

**DiskANN / FreshDiskANN (graph, for contrast).** DiskANN keeps compressed vectors in RAM and a Vamana graph on SSD. FreshDiskANN (Singh et al., arXiv 2021) is the graph world's LSM-like answer to updates. A Long-Term Index lives on SSD with only about 25–32 bytes of PQ-compressed data per point in RAM. New inserts go into an in-memory read-write TempIndex that is periodically frozen into read-only TempIndexes. Deletes go to a DeleteList: deleted points still help navigation but are filtered from results. Search queries the LTI plus every TempIndex and merges results. When TempIndexes pass a memory threshold, **StreamingMerge** builds a new LTI over (P∪N)\D in three phases (delete-repair, insert, patch) with two sequential SSD passes, using memory proportional to the change set rather than the index. Reported results on an ~800M-point SIFT1B subset: merging a 10% change took about 10% of a full rebuild's time; the system sustained 1,800 inserts/s and 1,800 deletes/s with sub-millisecond update latency and 1,000 searches/s at >95% 5-recall@5, all within 128 GB of RAM. The authors avoided direct SSD inserts because each would cause up to R (64–128) random writes. This is a very useful reference architecture for Quickwit's merge pipeline even if you pick IVF: an in-memory fresh index, immutable long-term indexes, tombstones, and a streaming merge whose cost scales with the delta.

**Elasticsearch DiskBBQ (IVF inside Lucene segments).** Elastic describes DiskBBQ as "an evolution of an Inverted Vector File (IVF) index" that "uses Hierarchical K-means to partition vectors into small clusters" and queries "at most 2 layers of the centroids," then bulk-scores the vectors in chosen clusters with Better Binary Quantization (BBQ). Elastic says it "typically performs well for recall levels up to around 95%" and requires 8.18+. Elastic's k-means engineering post reports that hierarchical k-means gave slightly higher within-cluster sum of squares (WCSS) than flat k-means. Its fix is a refinement pass where each vector only considers a shortlist of neighboring clusters (cheap because segments reach only "10s of millions of vectors"), plus SOAR-style spill assignments at about the cost of one k-means iteration. Later posts add two centroid tiers (coarse "query centroids" reused across child "document centroids," 5× faster query quantization) and merge-time auto-calibration of quantization parameters per segment. This is the most directly transferable prior art for Tantivy: IVF as a per-segment codec, rebuilt or refined on merge.

**Quake (OSDI 2025).** A multi-level IVF where "each level is a partitioned index similar to Faiss-IVF," with centroids recursively partitioned. A cost model built from partition sizes *and access frequencies* decides which partitions to split or merge, and a recall-estimation model sets `nprobe` per query as the structure changes. The authors report 1.5–8× lower search latency than HNSW, DiskANN and SVS, and 6–83× lower update latency, on dynamic workloads (the arXiv abstract also cites up to 38× and 126× headline figures). Its evaluation says LIRE suffers "recall degradation, partition explosion" and DeDrift a latency increase on Wikipedia-12M.

**LSH.** Locality-sensitive hashing (e.g., p-stable LSH, Datar et al. 2004) partitions by random projections, not learned centroids. It is data-independent, so it never drifts, and merging is trivial because hash buckets from two splits combine by union. The price is poor recall per byte read versus learned partitioning. None of the object-storage systems reviewed here use LSH as their primary index. Pinecone uses "random projections" only for fast indexing of fresh L0 slabs (see §3). LSH is a reasonable choice for a *freshness tier* or for split-level sketches, not the main index.

## 2. Content-Based Document Clustering for Text Search Efficiency

**The cluster hypothesis.** Jardine & van Rijsbergen (1971, *Information Storage and Retrieval* 7(5)) reported on a Cranfield subset that "cluster-based retrieval strategies can be devised which are as effective as linear associative retrieval strategies and much more efficient." van Rijsbergen's textbook states it canonically: "closely associated documents tend to be relevant to the same requests," and if it holds, clustering "will not only speed up the retrieval but may also make it more effective." This is the theoretical basis for everything below. Note that it concerns *relevance*, so it transfers to ranked/semantic queries better than to exact pattern or grep-style log queries.

**Cluster-skipping inverted indexes.** Altingovde, Demir, Can & Ulusoy (ACM TOIS 26(3), 2008) put "cluster membership and centroid information along with the usual document information into a single structure." Best clusters and their best documents are computed "with a single posting-list access per query term," and "only relevant portions of the posting lists corresponding to the best clusters are considered and the rest are skipped." They report "substantial efficiency improvement while yielding comparable, or sometimes better, effectiveness" in compressed settings. This is the text-side analog of IVF *within* an index: postings grouped by cluster, with skipping driven by centroids.

**Selective search / topical sharding.** Kulkarni & Callan (CIKM 2010; TOIS 33(4), 2015) partition a corpus with k-means into topical shards. A resource-selection algorithm (e.g., Rank-S, Taily) picks a few shards per query, and effectiveness stays "on par with that of exhaustive search"; Kim, Callan, Culpepper & Moffat (ECIR 2016) report that it evaluates fewer postings, "often resulting in 90+% reductions in querying cost." Kim, Callan, Culpepper & Moffat (*Information Retrieval Journal*, 2017) confirmed at fine-grained simulation that selective search "is significantly more efficient than conventional distributed search architectures." On Gov2 it handled "four to five times the rate of queries as exhaustive search before saturating." Such systems use few, large clusters (Dai, Kim & Callan, CIKM 2016, note that Kulkarni and Callan "split 50 million documents into 100 clusters of 500 thousand documents each"), unlike classic cluster retrieval's many small ones. Also, "collections organized by topic require global idfs for the best performance" when merging results. That is a real cost for Quickwit, whose BM25 is computed per split. Topical shards also compose with in-shard dynamic pruning: "the computational gains from topical sharding and pruning are additive."

**Doc-ID reordering by recursive graph bisection (BP).** Dhulipala et al. (KDD 2016) reorder document IDs to minimize log-gaps between postings. On Gov2/ClueWeb09/FB-Posts they report "a 22% and a 15% compression improvement over alternatives," and Mackenzie et al. (ECIR 2019) reproduced the core results. Lucene 9.8 shipped this as `BPIndexReorderer` (changelog entry GITHUB#12489: "more compact postings and faster queries, especially conjunctions"), and `BPReorderingMergePolicy` "reorders merged segments according to a BPIndexReorderer." Lucene's docs say it has "been observed to also speed up queries significantly by clustering documents that have similar sets of terms together." Lucene committers have proposed applying the same idea to KNN graph node IDs and even to shard assignment. Adrien Grand calls BP a main reason PISA is fast but "a heavy contributor to the indexing time." For Quickwit/Tantivy, BP is the cheapest content-clustering win: it runs at merge time and needs no change to split routing.

## 3. Object-Storage-Native and Disaggregated Search Architectures

**turbopuffer.** Object storage is the source of truth; memory and NVMe are caches. The vector index is "based on SPFresh," extended by "nesting clusters hierarchically in a multi-dimensional tree structure" with ~100 children per node. ANN v3 reports 200 ms p99 latency over 100+ billion vectors at 1k QPS and 92% recall. Key engineering numbers: about 500 clusters of 100 vectors searched per machine per query; the lowest (data) level is SSD-bandwidth-bound at about 100 QPS until RaBitQ binary quantization (16–32× compression) is added. Fewer than 1% of candidates need full-precision reranking. For 100B-scale deployments turbopuffer sizes nodes to keep the whole tree on SSD, since object storage bandwidth (<5 GB/s) is too low for data-vector reads. So "clusters fetched lazily from S3" is the cold-start path, not the steady state at extreme scale. turbopuffer's write/compaction internals are only partly public (WAL on object storage, an LSM storage engine for index files, compare-and-swap-coordinated commits per third-party summaries). The SPFresh rebalancing it runs is described only at a high level ("dynamically splits and merges clusters to maintain balance," so the index "doesn't need to be periodically rebuilt").

**Pinecone serverless.** Blob storage is the source of truth. Writes are logged, a freshness layer serves recent data, and an index builder produces "a geometrically partitioned index," keeping "centroid vectors as representatives of each partition." The newer slab architecture is explicitly LSM-like. A memtable flushes to immutable L0 slabs indexed with "fast indexing techniques like scalar quantization or random projections." As slab counts grow, "compaction kicks in," and it is there "that we build more computationally intensive partition- or graph-based indexes," amortizing index cost over the slab's lifetime. This is the closest published analog to Quickwit splits plus merge pipeline: cheap indexes on young splits, expensive clustering on mature merged splits.

**LanceDB / Lance.** Disk-first IVF-PQ (plus IVF-RQ/RaBitQ and HNSW variants) over Lance's columnar fragments on object storage. A Lance design issue shows the drift problem concretely. Users set a fixed `num_partitions`, so the maintainers propose a `target_partition_size` (default 4096) with `num_partitions = min(num_rows / target_partition_size, sqrt(num_rows), max_partitions)`. `optimize_indices` "should automatically handle retraining IVF" once partition count has "drifted far enough" from ideal. Lance's pattern is thus append-to-existing-centroids with periodic retrain, a pragmatic baseline.

**Milvus / Zilliz.** Growing segments are brute-force searchable. Sealed segments get per-segment IVF/HNSW/DiskANN indexes stored on S3/MinIO. Data nodes merge small sealed segments up to 1 GB by default and compact once deletions pass 20%. Milvus's **clustering compaction** is the most explicit production example of content-aware segment layout. It "redistributes the data according to value of the clustering key field, split by range" and stores `partitionStats` metadata so queries can prune segments "like a global index." Milvus reports up to a 25× improvement on a 20M-vector LAION benchmark with range-filtered searches. Milvus "already supports vector-based clustering compaction to reorganize data by vector similarity," and an open issue (#52175) plans a global vector index that uses that clustering information "to identify relevant sealed segments for each query, allowing Milvus to prune unrelated segments before executing vector search." That is exactly the split-pruning design Quickwit would need, and it is not yet shipped as of that issue.

**Amazon S3 Vectors.** A vector bucket type with native query APIs. At GA (Dec 2025) it supports up to 2 billion vectors per index, 10,000 indexes per bucket, sub-second latency for infrequent queries and about 100 ms for frequent ones, 1,000 vectors/s streaming writes, and 50 metadata keys per vector. AWS does not disclose the index algorithm, so it is useful as a cost and latency benchmark but not as design prior art.

**Quickwit today.** Splits carry min/max timestamps and a set of tags. Tag metadata is generated only when the field's cardinality is under 1,000. The root searcher prunes splits by time range and tags before fanning out with rendezvous hashing. The default `stable_log` merge policy merges similar-size, time-adjacent splits "to minimize write amplification AND keep time-pruning power as high as possible." A partitioning key can route documents to different splits. That is the hook for content-based routing: a coarse-centroid ID could serve as a partition key.

**Zone maps, bloom filters and summaries.** All the pruning mechanisms above are summary structures: min/max ranges (Quickwit time pruning, Milvus `partitionStats`), low-cardinality tag sets (Quickwit tags), and centroid sets (IVF). A split-level centroid set or a list of coarse-cluster IDs present in the split is simply a zone map for vector space. Its pruning power depends entirely on whether splits are content-clustered. With purely time-ordered splits, each split covers most of the embedding space and centroid-based split pruning prunes almost nothing.

## 4. Hybrid Text + Vector Search: Reconciling Two Pruning Strategies

**The problem.** turbopuffer's analysis gives the canonical trade-off. Pre-filtering reaches 100% recall but costs O(dimensions × matches) (10 s in their example). Post-filtering can reach 0% recall when none of the nearest neighbors match (20 ms). Their target is 90% recall at 25 ms, which is "not achievable with query planner hacks unless the vector and the filtering indexes cooperate."

**turbopuffer native filtering (cluster-aware inverted indexes).** Each document gets a vector-index address `{cluster_id}:{local_id}`. Attribute indexes are stored in the LSM as `(attribute_value, cluster_id) → Set<local_id>` bitmaps, and they must be updated when SPFresh moves a document. A downsampled cluster-level version lets the planner compute "the set of relevant clusters" before fetching row bitmaps, so the plan becomes "find the nearest clusters that contain at least one match." It also keeps cold-query round trips low. turbopuffer samples 1% of live queries to measure recall continuously, targeting 90–95% recall@10 including filtered queries. For Quickwit this means Tantivy postings for filterable fields should also be available at *cluster granularity* inside a split (a per-term bitmap of cluster IDs), so a filtered ANN query can skip clusters with no matches.

**ACORN (SIGMOD 2024).** A graph-side answer. HNSW is built with denser neighbor lists so that the subgraph induced by any predicate stays navigable. At search time it traverses only predicate-passing nodes, with 2-hop expansion, and falls back to pre-filtering below a configured minimum selectivity. It reports 2–1,000× higher throughput at fixed recall than prior methods. Weaviate ships an ACORN-inspired filter strategy. Its relevance to Quickwit is mostly as a contrast: a cluster-based index gets a simpler filter integration (cluster-level bitmaps) than graph indexes do.

**Segment-level co-pruning.** Milvus's scalar clustering compaction plus `partitionStats` prunes *segments* by filter before vector search. Pinecone describes adaptive metadata filtering inside slabs, and its ICML 2025 paper covers accurate metadata filtering in its architecture. The general lesson: apply the cheapest summary first (time/tag/zone map at split level, then cluster-level attribute bitmaps, then centroid distance, then row bitmaps), and have the planner switch to brute-force over matches when a filter is very selective.

**Text relevance plus vectors.** turbopuffer, LanceDB, Milvus and Elasticsearch all run BM25 and ANN as separate retrievers fused with methods like RRF. None of the sources reviewed describes one physical partitioning that is optimal for both lexical and semantic pruning. Selective search's topical shards and IVF clusters are conceptually the same move (k-means on content), which suggests one embedding-based coarse partitioning could serve both. That is an inference, not an established result.

## 5. Merging and Compacting Clustered Structures Without Full Re-Clustering

| Technique | Mechanism | Cost model | Relevance to Quickwit merges |
|---|---|---|---|
| Append to frozen centroids (Faiss IVF, Lance, Milvus growing segments) | Assign new vectors to nearest existing centroid | Near zero; quality decays with drift | Baseline; fine for young splits |
| Periodic retrain (Lance `optimize_indices`, segment rebuild in Milvus/Lucene) | Re-run k-means on the merged data | Full cost per merge, grows with index | What DiskBBQ/Milvus do per segment today |
| Centroid-seeded merge (reported for Elasticsearch `HierarchicalKMeans.clusterByConcatenation/Insertion`) | Input segments' centroids seed the merged tree; one assignment pass, "zero Lloyd iterations," with guards for degenerate cases | About one assignment pass | **Best fit for split merges** |
| SPFresh/LIRE | Split oversized partitions, merge small ones, reassign boundary vectors | Local, proportional to changed partitions | Apply at merge to fix imbalance |
| DeDrift | Lazy: recompute centroids from assigned vectors; Split: split large clusters and absorb small ones, keeping count constant | "Up to 100× faster than a full index reconstruction" | Cheap centroid refresh at merge |
| Ada-IVF | Maintain only partitions that are accessed or imbalanced (only 15% of partitions were searched per day in an industrial workload) | LIRE made 3× as many partitions and took 4× the update time for similar QPS | Prioritize maintenance of hot splits |
| Quake | Cost model (size × access frequency) triggers split/merge; per-query `nprobe` via recall estimator | Continuous, converges to local minimum | Merge policy informed by query stats |
| Pinecone slab compaction | Cheap indexes (SQ/random projections) on L0; partition/graph indexes built on compaction | Amortized over slab lifetime | Tiered index quality by split maturity |
| FreshDiskANN StreamingMerge | Temp in-memory index + delete list merged into long-term index in sequential passes | About 10% of rebuild time for a 10% change | Architecture template for freshness |

**Centroid-seeded merging.** A third-party engineering issue (serenedb) describes Elasticsearch's IVF merge code this way. `TieredMergeStrategy` with `HierarchicalKMeans.clusterByConcatenation` or `clusterByInsertion` makes "the centroids of the inputs become the seeds for the merged tree," with "one assignment pass, zero Lloyd iterations, plus guards for the degenerate cases where reuse would produce a bad tree." It also mentions balanced k-means via entropic optimal transport (Sinkhorn). This is secondhand evidence about Elastic's code, not an Elastic publication, so check it against the Elasticsearch source before relying on it. The approach is still sound and cheap: it is Lloyd's algorithm warm-started from a very good initialization.

**Drift characterization.** Ada-IVF shows imbalance and reconstruction error rising steadily under inserts and deletes, tracking latency degradation. It also found skewed access: only 3% of partitions were accessed by more than ten queries in a day. DeDrift shows that both query and database distributions shift in real media workloads, and that updating quantizers on the fly "almost eliminates the accuracy degradation."

**Text-side merges.** BP reordering is recomputed per merged segment by `BPReorderingMergePolicy`. It is not incremental, but it is local to the merge. Selective-search papers assume a static corpus; incremental topical-shard assignment of new documents to existing shard centroids is the obvious extension, and it inherits the same drift issues as IVF.

## Recommendations for Quickwit

1. **Start with a per-split IVF codec (the DiskBBQ/Pinecone pattern).** Store centroids (and optionally a two-level centroid tree) in the split footer/hotcache, and store each cluster's quantized vectors as one contiguous byte range so a query needs about two range-GETs per split: hotcache, then the chosen clusters. Use RaBitQ/BBQ-style binary codes in the cluster blocks, keep full-precision vectors in a separate range for rerank (turbopuffer reranks <1%), and add SOAR-style spill assignment for recall. This works with time-ordered splits and needs no metastore changes.
2. **Make merges centroid-reusing, not re-clustering.** Seed the merged split's k-means with the union of input centroids, do one assignment pass, then run LIRE-style local fixes (split oversized clusters, merge tiny ones, reassign boundary vectors) and a DeDrift-lazy centroid recompute. Borrow Pinecone's tiering: young splits get a flat or coarse index (or even brute force), and IVF quality rises with merge level.
3. **Add split-level pruning only if you also add content-based routing.** A split-level centroid summary in the metastore prunes nothing on time-ordered splits. To get turbopuffer/Milvus-style cross-split pruning, train a global coarse codebook (e.g., 256–4,096 centroids), stamp each document with its coarse cluster ID at indexing, use that ID as the partition key (or as a high-cardinality "tag"), and store per-split coarse-cluster membership in the metastore. Then add a merge policy that groups by coarse cluster as well as time (a variant of `stable_log`). This trades time-pruning power for vector-pruning power, so make it opt-in per index. It is essentially the global index Milvus has proposed but not yet shipped.
4. **Make Tantivy filters cluster-aware.** Emit per-split, per-term cluster-ID bitmaps (turbopuffer's downsampled index) so filtered ANN can skip clusters with no matches, and fall back to exact kNN over the filtered doc set when the filter is highly selective (ACORN's s_min idea).
5. **Get BP reordering for text for free.** Port Lucene's `BPReorderingMergePolicy` idea to Tantivy merges for smaller postings and faster conjunctions. It is independent of the vector design.
6. **Measure recall continuously.** Sample a small share of production queries for exact-vs-approximate comparison as turbopuffer does, since drift and merge shortcuts degrade recall silently.

## Caveats

- Vendor performance numbers (turbopuffer, Pinecone, Milvus, Elastic, AWS) are self-reported on the vendor's own benchmarks. Competitor critiques of SPFresh (Yi, LSM-VEC) and Quake's comparisons are also on the authors' chosen workloads.
- turbopuffer's and Pinecone's internals are only partly documented. Details like turbopuffer's compaction mechanics come partly from third-party summaries and an unofficial reimplementation, and are not authoritative.
- The Elasticsearch centroid-seeded merge description comes from a third-party GitHub issue, not Elastic documentation.
- No quantitative Lucene benchmark for BP query speedups was found in primary sources; only qualitative statements ("sizable gains," "significantly") are available. Likewise, the cluster-skipping index's efficiency gains are described only as "substantial" in the abstract.
- The cluster hypothesis and selective search concern ranked relevance. Their benefit for exact-match log queries (Quickwit's core workload) is unproven, and topical sharding weakens time-range pruning and complicates per-split BM25 statistics.
- Several sources (Quake, Ada-IVF, DeDrift) evaluate in-memory indexes; their maintenance ideas transfer to object storage, but their latency numbers do not.
